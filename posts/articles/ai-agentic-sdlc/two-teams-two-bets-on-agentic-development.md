# Two Teams, Two Bets on Agentic Development: A Case Study

> **TL;DR:** One team built an agentic pipeline around narrow, task-scoped agents — one for bug-fixing, one for code review, one for test generation — each carrying a small, explicit rulebook and stopping for human confirmation at specific, well-placed checkpoints. Another team, modernizing a much larger legacy system, took a different bet: broad, role-scoped "persona" agents (a coder, a builder, a reviewer, a scrum master) each mapped to one architectural module, backed by a documentation format built specifically to be machine-readable, with the human role shifted toward observing a timed work period and codifying whatever emerged afterward. Neither approach is finished, and — as this piece lays out with current industry research — neither is unprecedented. Both patterns show up independently across the industry, and comparing them surfaces exactly where each one is well-supported by evidence and where each is still an open bet.

## Why put these two side by side

It's tempting to describe "an AI SDLC" as if it were the only reasonable way to apply agents to software development, especially when you understand one version of it from the inside. But two structurally different approaches to the same underlying idea — let AI agents do more of the actual implementation work, and shrink the human's role toward direction and judgment rather than typing — are both being tried in the real world right now, by different teams solving different problems. Comparing them isn't about declaring a winner. It's about noticing that "agentic SDLC" is a category, not a single recipe, and the specific choices inside that category — how narrow an agent's scope is, how autonomy is bounded, what the human actually spends their remaining time on — matter enormously to whether an approach holds up under real work.

## The two starting points

The first approach sits inside a from-scratch mobile app rewrite: a known target architecture (clean layering, a settled state-management approach, a settled set of conventions), being built out feature by feature, with agents layered on top of an already-decided structure. The work agents do is mostly "implement this specific, well-bounded thing correctly within rules that are already settled."

The second approach sits inside a much larger and more architecturally ambitious effort: carving a large legacy monolith — a decades-old, business-critical product — into a modular structure built around domain-driven design's "bounded contexts." Several dozen of these modules have been identified and named as the eventual target. As of this writing, only one is actually built out; the rest exist only as claimed names reserving a namespace for later. That's an important detail to hold onto throughout this comparison: everything interesting about the second approach is happening inside a single pilot module, not across a mature, running system. That bet is being tested in the hardest possible place — figuring out how to carve one module out of a monolith at all — before it's been tested at the thing it's ultimately for, which is doing that many more times over.

For clarity, this piece refers to them as the **task-scoped team** and the **persona-scoped team** — descriptive labels for the pattern each one chose, not names of specific organizations.

## How each team actually gets an agent to behave

The real engineering artifact in both cases isn't a clever prompt typed once — it's a written set of instructions, and the shape of those instructions differs sharply between the two approaches.

The task-scoped team's agents are scoped to a single pipeline stage and carry a narrow, specific rulebook for exactly that stage. A test-generation agent's entire instruction set is about deciding what's worth a unit test and what isn't — a decision matrix, not a philosophy. A bug-fixing agent's instructions are about triage and root-cause investigation, checked against a written severity rubric, and nothing else. Each agent knows a little, precisely.

The persona-scoped team's agents are scoped to a role, not a pipeline stage, and mapped to the one architectural module that currently exists. A "coder" persona for that module carries a genuinely long instruction document — architecture principles (domain-driven design, a specific ordering of design principles the team prioritizes when they conflict), explicit prohibitions ("never guess at a name — verify it against documentation or the legacy source before using it"), and guidance on when to stop and ask a human rather than proceed on an assumption. There isn't just a coder; there are distinct personas for building, for reviewing, for writing pull requests, for triaging bugs, for root-cause analysis, and one framed around sprint facilitation, each with its own document. Each agent knows a lot, about one thing.

| | Task-scoped pattern | Persona-scoped pattern |
|---|---|---|
| Agent scoped to | A pipeline stage (bug-fix, review, test-gen, PR) | A role, applied to one architectural module |
| Instruction depth | Narrow and specific (a rule, a matrix) | Broad and principle-heavy (an architecture philosophy) |
| Applied against | An already-settled target architecture | A legacy system being actively carved up |
| Number of agents | Several, each thin | Several, each thick |
| Maturity, as observed | Running across most of an app in production | Proven in one pilot module out of several dozen planned |

Neither shape is obviously superior in the abstract, and this isn't a fringe disagreement — it maps onto two patterns actively studied and deployed across the industry, covered in more depth below. A thin, task-scoped agent is easier to verify and easier to trust incrementally — it's hard for a rulebook about "what's worth a unit test" to go badly wrong in a way that's also hard to notice. A thick, role-scoped agent carrying real architectural judgment is a bigger bet per agent, but it's also doing more per invocation, which matters more when the target architecture itself isn't settled yet and every implementation decision is also, implicitly, a decision about the target shape.

## Where this sits in the wider industry

Both patterns turn out to have real names and real research behind them, independent of either team.

The task-scoped pattern lines up with what industry analysts currently call **task-specific agents** — Gartner projects these will [appear in 40% of enterprise applications by the end of 2026](https://www.gartner.com/en/newsroom/press-releases/2025-08-26-gartner-predicts-40-percent-of-enterprise-apps-will-feature-task-specific-ai-agents-by-2026-up-from-less-than-5-percent-in-2025), up from under 5% in 2025 — and with the broader discipline researchers call [context engineering](https://sourcegraph.com/blog/context-engineering): deliberately curating what an agent sees and checks against, rather than relying on a well-phrased prompt. A 2026 survey found 82% of IT and data leaders now agree prompt engineering alone isn't sufficient for production use, which is close to the task-scoped team's whole operating premise.

The persona-scoped pattern lines up just as directly with published multi-agent research. [MetaGPT](https://github.com/FoundationAgents/MetaGPT) assigns a Product Manager, Architect, Project Manager, Engineer, and QA Engineer as distinct personas collaborating through a shared message pool, built on the thesis that software quality comes from well-defined procedures executed by specialized roles rather than from one generalist doing everything. [ChatDev](https://starlog.is/articles/ai-agents/foundationagents-metagpt) goes further, modeling an entire virtual company with roles like CEO, CTO, Programmer, and Reviewer. The persona-scoped team's "coder," "reviewer," and "scrum-facilitation" personas mapped to one module are a real-world instance of a pattern that's been named and studied, not a one-off invention.

There's also a directly relevant standard worth knowing regardless of which pattern a team leans toward: [AGENTS.md](https://agents.md/), an open specification for a repo-level instructions file that tells any AI coding agent how to build, test, and behave in a given codebase. It was formalized in 2025 with backing from OpenAI, Google, Cursor, and Factory, donated to the Linux Foundation in December 2025, and adopted by tens of thousands of repositories since. Both teams' agent-instruction documents are, in effect, hand-rolled versions of what AGENTS.md now standardizes.

## Documentation as an interface, not just a reference

One of the more distinctive choices in the persona-scoped approach is treating documentation itself as something built for agent consumption, not merely available to an agent the way it's available to a person. Its architecture and planning documentation lives in a constrained, structured format with its own explicit authoring rules, specifically because that's the format its tooling and agents are set up to parse and edit reliably. That's a real constraint to put on human writers, and a deliberate one: the documentation isn't just written *about* the system for whoever reads it later, it's written *as* an interface the agents themselves operate against.

The task-scoped approach's documentation, by contrast, is mostly prose instructions plus, for the highest-stakes architectural rules specifically, a small number of deterministic scripts that check a rule mechanically rather than asking an agent to interpret prose correctly every time. That's a narrower, more surgical version of the same underlying insight — natural-language instructions are ambiguous enough that an agent (like a person) can talk itself into a wrong interpretation, so for the rules where that ambiguity is expensive, don't leave it in prose form at all.

Both are, independently, rediscovering **Architecture Decision Records** — [a documentation format formalized well over a decade ago](https://www.nexapp.ca/en/blog/architecture-decision-records-adr) for capturing context, options considered, a decision, and its consequences, now being [explicitly repurposed as machine-checkable input for AI agents](https://mnemehq.com/insights/how-ai-coding-agents-use-adrs/) rather than just human reference material. It's worth being honest about the trade-off each choice makes. A structured, agent-native documentation format is more work to author and maintain — a contributor writing an architecture note now has to follow a stricter format than a quick note, which is real friction on the human side, paid specifically to reduce ambiguity on the agent side. A handful of narrow enforcement scripts is cheaper to introduce but only covers the specific rules someone thought to write a script for; everything else is still riding on prose being interpreted consistently.

## Where the human actually steps in

This is probably the sharpest philosophical difference between the two approaches, and it's also where current industry evidence has the most to say.

The task-scoped pipeline places confirmation gates immediately before specific, hard-to-reverse actions — before a bug fix is marked resolved, before a set of files actually gets committed, before a pull request is opened against a protected branch. The philosophy is: let the agent do as much as it wants right up until a step that would be expensive to undo, then make a person look at exactly that one thing and confirm it explicitly.

The persona-scoped approach is closer to a supervised autonomy loop running on a timer than a series of checkpoints. Agents are given a role and a scope and allowed to work across a defined period largely uninterrupted, and the human's real work happens *after* that period closes: reviewing what actually got built, recognizing which of the emergent patterns were good ones, and formally codifying those patterns into lighter-weight process for next time. The human role isn't absent, but it's retrospective rather than interstitial — closer to being an editor reviewing a finished draft than a checkpoint reviewer stopping the presses mid-run.

Current research suggests this distinction matters more than it might first appear. A 2026 study found the share of organizations requiring human review before high-risk AI actions [dropped from 40% to 25% in six months](https://www.prnewswire.com/news-releases/new-study-most-organizations-have-abandoned-human-ai-oversight-302825345.html), while the share running agents with full autonomy and no review more than doubled. The [2026 International AI Safety Report](https://www.insideprivacy.com/artificial-intelligence/international-ai-safety-report-2026-examines-ai-capabilities-risks-and-safeguards/) treats that direction as a genuine risk, and separate quality research backs the concern with numbers: one large-scale study found that [61.4% of agent-authored pull requests in its sample were merged immediately after automated checks passed](https://hackernoon.com/research-shows-ai-is-writing-more-code-but-teams-still-lack-adequate-review-standards), with human reviewers often reducing their involvement to an unexamined approval. That data leans toward validating the task-scoped pipeline's narrow, pre-action gates specifically *because* they sit before the action becomes irreversible — though it's fair to note the persona-scoped team's retrospective review is happening inside one tightly scoped pilot module with presumably close attention, not at the scale where the concerning industry statistics were measured. Research on [graduated human oversight](https://arxiv.org/pdf/2606.22484) — scaling review intensity to how consequential and reversible an action is — describes something close to a middle path between the two philosophies, worth either team studying further.

## Institutional memory: two different shapes of "we tried that and it didn't work"

Both approaches include a mechanism for remembering what didn't work, and the mechanisms look different in a way that reflects each philosophy.

The task-scoped team's decision matrices are, in effect, distilled lessons — "don't ask an agent to just add tests, because without a specific rule it'll happily generate coverage-padding tests for generated code" is a lesson folded directly into an operational rule an agent checks every time. The lesson becomes a permanent, load-bearing part of the pipeline, not a document someone has to go read.

The persona-scoped team keeps something closer to a literal historical record — a dedicated archive of superseded proposals and retrospectives, preserved rather than deleted, each with the reasoning for why it was superseded. One clean example: an early proposal called for a formal dependency-tracking registry between modules. Once the team was a few iterations into building the one pilot module, that registry was explicitly rejected as premature — with only one module actually built, a lightweight, convention-based approach to detecting what needs rebuilding was judged sufficient, and the heavier registry was shelved with that reasoning written down rather than quietly dropped. That's a healthy instinct almost regardless of the rest of the approach: resisting the urge to build process or tooling for a scale problem you don't have yet, and writing down why, so the next person with the same instinct can read the reasoning instead of relitigating it from scratch.

There's also a concrete, almost mundane example of institutional memory paying off: a toolchain regression. The persona-scoped team hit a real bug in a specific patch version of their build toolchain's SDK that broke dependency restoration for a newer solution-file format they'd standardized on — every affected project failed to restore identically. Rather than patch around it quietly in one place, the team documented the exact symptom, pinned the known-working SDK version as the default, and added a narrow build-flag workaround at every site that invoked the affected command, with an explicit note to remove the workaround once a fixed SDK version was verified installed everywhere. That's the kind of friction any team pushing agents to do more implementation work is going to hit sooner or later — the tooling underneath the agents has its own bugs, and an agent working from stale or incomplete knowledge of a toolchain quirk will cheerfully reproduce a failure a human would have recognized on sight.

## What "the developer just provides context" actually costs

The framing that AI should do essentially everything and a developer's job should shrink to providing context is appealing, and it's also easy to understate what "providing context" actually requires once you look at what it takes to make it real. On the persona-scoped side, "the context" isn't a paragraph in a chat window — it's an entire documentation subsystem, built in a specific machine-parseable format, with its own authoring rules and its own tooling. Writing and maintaining that is substantial, ongoing engineering work in its own right, done by humans, for the specific purpose of making an agent's job possible. On the task-scoped side, "the context" is smaller in scope but no less real — a decision matrix doesn't write itself, a severity rubric doesn't write itself, and the small enforcement scripts that check the highest-stakes architecture rules mechanically had to be written and have to be kept current as the architecture evolves.

The honest version of "AI does everything, the developer just provides context" is closer to: a meaningful fraction of what used to be implementation work has moved into a different kind of work — writing, structuring, and maintaining the context and the rules an agent operates inside of — rather than disappearing. That's still a real shift, and plausibly a good one; measured well, it should mean less time on repetitive implementation and more time on the judgment calls that actually require it. But it's not a shift toward less work overall, and describing it that way to anyone evaluating whether to try something similar would be setting the wrong expectation from the start.

## What each approach could take from the other

A few things seem genuinely worth borrowing in each direction.

The task-scoped pipeline's narrow, pre-commit confirmation gates seem like a cheap, valuable addition to a role-scoped, review-after-a-period model — not a replacement for the retrospective review, but a smaller, earlier safety net specifically around the handful of actions that are expensive to undo (a merge, a schema change, anything touching data at rest). A model that's otherwise fine reviewing work after a period closes doesn't have to extend that same patience to the one or two step-types where a mistake compounds fastest.

Conversely, the persona-scoped team's archive of rejected approaches — preserved with the reasoning behind rejecting them — seems like a genuinely useful pattern for a task-scoped team to adopt directly, distinct from its decision matrices. A decision matrix captures "here's the rule now"; it doesn't capture "here's the more elaborate thing we considered and specifically decided against, and why," which is exactly the kind of context that prevents a good idea that turned out to be premature from getting re-proposed and re-litigated by someone (or some agent) who wasn't there the first time.

And the instinct to explicitly resist building process ahead of actual need — rejecting a dependency registry because one module doesn't yet justify it — is a discipline worth naming and holding onto deliberately as any agent tooling effort grows, since the natural tendency is to keep adding structure, and the moment to ask "do we actually have the scale problem this solves yet" is easy to skip past when building forward rather than looking back.

## What's still genuinely unproven, on both sides

Neither approach should be read as validated by this comparison, and it's worth being precise about exactly what's untested in each — the industry evidence above supports pieces of each philosophy, not a verdict on either as a whole.

For the task-scoped pipeline: the confirmation-gate model has been running across most of a real production app, which is meaningful real-world exposure, but it hasn't been stress-tested against agents that need to coordinate architectural decisions *across* features rather than implement within an already-settled structure — these agents mostly execute within a target architecture that was decided by humans up front, which is a different and probably easier problem than deciding the target architecture itself.

For the persona-scoped approach: the entire pattern has been validated in exactly one module, deliberately the simplest and most self-contained one to pilot with. Whether role-scoped persona agents, a retrospective review cadence, and an agent-native documentation format all continue to work once there are several modules running concurrently — with cross-module dependencies, shared review attention spread thinner, and genuinely more surface area for something to go wrong between review periods rather than within one — is the actual test this approach hasn't faced yet. The deliberate refusal to build a cross-module dependency registry "yet" is itself an acknowledgment that the harder, multi-module version of this problem is still ahead, not behind.

## Takeaways

- "Agentic SDLC" isn't one recipe — task-scoped agents with narrow rulebooks and role-scoped persona agents with deep architectural context are both legitimate, structurally different bets, each with real precedent in published industry research (task-specific agents and context engineering on one side, MetaGPT- and ChatDev-style multi-agent frameworks on the other).
- Where a human checks in matters as much as whether they check in — and current safety and quality research leans toward narrow, pre-action gates over purely retrospective review, though the comparison isn't a clean verdict given the very different scale each approach has been tested at.
- A documentation format built specifically for agent consumption is a genuine lever, but it moves cost rather than removing it — both approaches here are, independently, rediscovering Architecture Decision Records, a well-established pattern now being explicitly adapted for AI consumption industry-wide.
- Preserving rejected ideas with their reasoning, not just the rules that survived, is valuable institutional memory that a pure decision-matrix approach doesn't naturally capture.
- "The developer just provides context" undersells what's actually happening — a real share of implementation effort has moved into building and maintaining the context and rules an agent works inside of, which is different work, not necessarily less work.
- Both approaches are validated at a scale smaller than their eventual target, and the honest next chapter for each is what happens when that scale increases.
